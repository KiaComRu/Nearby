# Защищённое сопряжение — Nearby 0.5.0

Этот этап добавляет защищённое прямое соединение двух установленных Windows-клиентов в общей локальной сети. Интернет, учётная запись и дополнительные платные услуги не нужны. На обоих ПК требуется Nearby 0.5.0. Телефонный QR/PIN и браузерный интернет-режим остаются отдельными способами подключения.

## Первое подключение

1. Установите 0.5.0 и откройте Nearby на обоих ПК.
2. Найдите второй ПК в «Устройства рядом» и нажмите «Сопрячь устройства». Если multicast блокируется, откройте «Подключиться к ПК», вставьте адрес из окна второго ПК и нажмите «Защищённое сопряжение по адресу». PIN для этого не нужен.
3. На обоих экранах появятся имя другого устройства и строка проверки из **8 групп по 8 символов**. Сверьте её полностью на настоящих экранах обоих ПК. Сравнения только начала/конца или имени недостаточно.
4. Если вся строка совпадает и вы узнаёте второй ПК, нажмите «Строки совпадают — подтвердить» на обоих. Если строки отличаются или запрос неожиданный — отклоните его. Запрос действует около 2 минут.
5. После двух подтверждений ПК появится в «Моих устройствах». Нажмите «Подключиться защищённо». В интерфейсе должно быть указано «TLS 1.3 · ключ устройства проверен».
6. Отправляйте файлы как раньше. Получатель подтверждает входящие файлы; раздача владельца доступна подключённому доверенному устройству. Входящие запросы через защищённый транспорт помечены TLS.

Имя устройства при создании ключа выбирается автоматически и сохраняется между запусками. В «Моих устройствах» можно переименовать другое устройство для себя: это меняет локальную подпись, не его ключ и не имя на другом ПК.

## Повторное подключение и отзыв

При следующем запуске ключи и список доверия сохраняются. Найденное устройство узнаётся по отпечатку сертификата, а не по имени или IP. Адреса из поиска используются только как подсказки; перед передачей ключ проверяется заново. При изменении IP/порта выберите актуальную карточку найденного ПК. Если поиск недоступен, можно указать актуальный адрес вручную; старый сохранённый адрес после перезапуска может перестать отвечать.

«Забыть устройство» удаляет его из местного списка доверия, закрывает активные соединения с ним и прерывает незавершённую передачу. Частичный входящий файл удаляется. Уже успешно полученные файлы не удаляются. Второму ПК отправляется уведомление об отзыве, если он доступен. Даже если уведомление не доставлено, этот ПК больше не принимает его защищённые запросы. Оставшаяся запись на отключённом втором ПК не сохраняет доступ; удалите её и выполните новое сопряжение при необходимости.

При смене ключа по известному адресу соединение прекращается **без автоматического перехода на HTTP**. Проверьте, какой ПК находится по адресу и не переустанавливались ли его данные, затем явно удалите старую запись и выполните новое сопряжение. Не подтверждайте неожиданную смену ключа по одному совпадению имени.

## Что шифруется и как проверяется доверие

У каждого клиента свой постоянный EC P-256 ключ и самоподписанный X.509-сертификат с SHA-256. Сертификат генерируется локально библиотекой selfsigned 5.5.0 (MIT) с использованием стандартных криптографических средств; файловая передача использует встроенный TLS Node.js, минимум TLS 1.3.

Для первого обращения разрешён только ограниченный TLS-пробник, который получает публичный сертификат без PIN, токенов, метаданных или файлов. Все следующие запросы закреплены за конкретным сертификатом: клиент задаёт его как доверенный и дополнительно сравнивает SHA-256 полного сертификата. После сопряжения сертификат берётся из сохранённого списка, не из нового недоверенного объявления.

HTTPS-сервер запрашивает сертификат клиента. Неизвестные сертификаты допускаются только к ограниченным API идентификации и сопряжения. Файловые API отдельно проверяют сохранённое доверие к точному сертификату при каждом запросе. Один сертификат без доступа к его закрытому ключу не позволяет пройти TLS-проверку владения ключом. Административные API и папки владельца по этому транспорту не предоставляются.

Строка первого сопряжения — полный SHA-256 канонического набора отпечатков обоих сертификатов, случайных значений обеих сторон и ID запроса, с отдельной меткой версии протокола. Она связывает подтверждение с конкретными устройствами и текущим запросом. Используется вся 256-битная строка, без сокращения до шестизначного PIN. Доверие записывается только после подтверждения обоих владельцев; сохранённое сопряжение не отменяет согласие на приём файла.

По TLS передаются API-запросы, имена и содержимое файлов, результаты и ссылки раздачи. Выданная защищённому устройству ссылка скачивания привязана к его сертификату и не работает через прежний HTTP-вход. Интерфейс владельца остаётся на HTTP loopback внутри Windows-окна; административный ключ не передаётся другому ПК. Шифрование транспорта не означает шифрование полученных файлов на диске.

TLS не защищает от скомпрометированной ОС, работы злоумышленника под вашей учётной записью или подтверждения строки без её реальной проверки. Это тестовая версия; независимый аудит протокола не проводился.

## Хранение ключей

Windows: `%LOCALAPPDATA%\Nearby\Data\device-identity.json`. Закрытый ключ и имя защищены Windows DPAPI в контексте **CurrentUser**. В файле находится зашифрованный блок; Nearby не отправляет его на хостинг, не пишет в логи и не включает в установщик. Для чтения/записи DPAPI используется скрытый процесс штатного Windows PowerShell, данные передаются через stdin/stdout, а не аргументы командной строки. Расшифрованный ключ нужен процессу для TLS и находится в его памяти.

`trusted-devices.json` рядом содержит публичные сертификаты, отпечатки, локальные имена, последние адреса и время сопряжения. Новые записи сохраняются атомарно. Повреждённое хранилище не обнуляется автоматически: запуск защищённого режима завершается с ошибкой, данные остаются на месте. Истёкший собственный сертификат также не заменяется незаметно; срок текущего сертификата — около 5 лет.

Обновление/обычное удаление программы сохраняет папку данных и полученные файлы. Не переносите файл идентичности на другой ПК и не публикуйте эти файлы. Копирование сертификата и ключа создаёт дубликат личности; DPAPI также ограничивает перенос между пользователями/машинами. Для нового устройства создавайте отдельное сопряжение.

Для запуска исходников вне Windows закрытый ключ хранится в файле с правами 0600; это отдельная модель защиты, не DPAPI. В тестах используется временное файловое хранилище, если явно не включена проверка DPAPI. `NEARBY_DISABLE_TRUSTED_LAN=1` выключает этот этап для специальных запусков; в обычной Windows-версии он включён.

## Совместимость и границы

Телефон через локальный QR/PIN по-прежнему использует HTTP в доверенной сети. На ПК также сохранён явно обозначенный старый HTTP/PIN-режим для прежних клиентов. Он не получает преимущества нового TLS-сопряжения; PIN не заменяет шифрование. Браузерный интернет-режим с прикладным шифрованием не менялся. Для шифрованной связи телефона и ПК используйте существующий интернет-режим на обоих устройствах.

Автопоиск теперь объявляет публичный отпечаток и отдельный TLS-порт. Объявления не содержат закрытых ключей/PIN и не устанавливают доверие. Старые 0.4-клиенты продолжают видеть обычный адрес, но для нового сопряжения должны обновиться. TLS-порт выбирается при запуске; брандмауэр не меняется автоматически. Ограничены размеры JSON, количество запросов и незавершённых сопряжений. Постоянное сопряжение через разные сети и отдельные мобильные приложения пока не добавлены.

## Проверки

`npm test` проверяет двухстороннее согласие, запрет файлов до подтверждения, недоступность административных API, неправильный сертификат, сохранение после перезапуска, повреждённые файлы состояния, невозможность скачать TLS-билет по HTTP и прерывание частичного файла при отзыве.

`npm run test:trusted` проверяет два независимых движка и браузерных окна: полную строку, два подтверждения, переименование, файлы 1 МиБ и пустой файл в обе стороны с SHA-256, перезапуск и повторное подключение без PIN, отзыв и мобильную ширину. `NEARBY_TEST_DPAPI=1` включает реальную DPAPI-защиту Windows во временных папках. Transport объявлений в этом сценарии моделируется; настоящий UDP отдельно проверяется `test:discovery`. Два физических ПК, их брандмауэры и роутеры ещё требуют испытания.
